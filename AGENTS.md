- Project code identity is `projects.revision`, advanced only inside the DB transaction that changes `project_files` (replace_project_files or per-statement file triggers); builds store `project_revision` and only a build of the current revision may affect readiness, the current-build pointer or publishing — why: stale build/verification results must never approve newer code.
- Generic design/craft prompt guidance lives only in `src/server/agent-knowledge/*.md` (Webby v1.2.30, loaded unedited via `?raw`, Webby-only tool sections filtered at load time); TS keeps runtime facts and deterministic enforcement — why: one canonical source per instruction category.
- Design-system packages live only in `src/server/design-systems/packages/<slug>/` (design.json, tokens.css, accents.json, fonts.html, DESIGN.md; optional preview.html, components/), validated by `design-systems/loader.ts`, applied deterministically by `apply.ts`, selection stored on `PicDesignSystem.package` and changed only by `retheme.ts` — why: one package format, no AI-driven re-theming, no second design store.
- The selected design-system package is the only authority for colours, fonts, tokens and accent; the Design Director, design-taste and app-UI blocks own composition/motion only and drop their palette/font instructions when a package is selected, and generation re-applies the package to the tree before commit — why: one visual authority, no competing palettes.
- Build outcomes go through `src/lib/build-outcome.ts` `decideBuildOutcome` and refunds through the guarded `refund_build_charge` (refuses ready/stale/same-revision-delivered builds); every variable cost is one append-only `cost_events` row with basis ACTUAL/ESTIMATED/ALLOCATED/UNKNOWN; free credits are build-only via `is_build_credit_reason` inside `spend_credit` — why: stale callbacks must never refund delivered work, and costs/credit purposes need one authority each.

- Requirement-level progress lives only on the PRD (`Prd.requirements`, `src/server/prd/prd-requirements.ts`); status is evidence-derived (COMPLETED only from a ready, verified build of the current revision; stays valid while its files are unchanged) and written by `prd-progress.server.ts` from generation and the build callback — why: one product memory, no model-claimed completion.
- Semantic source validation uses the real TypeScript checker (`src/server/verification/identifiers.server.ts`, TS2304 only, changed files only, explicit verified/failed/unavailable — unavailable follows the syntax-gate policy and is never reported as verified) inside `verifyProposedSource`; esbuild remains the parse gate — why: parse-only validation let `ReferenceError: mode is not defined` commit and crash the preview.
- Repair turns are classified BEFORE the design/PIC stages in `/api/generate` (`isRepairTurn`): they reuse the committed design direction via `readDirectionFromMemory` (never re-pick), skip structural-turn treatment, and emit truthful stage labels — why: a runtime-error repair must never restart first-build stages or disturb the design contract.
- Failure origin is classified once in `src/lib/failure-classification.ts`; only `code` failures may justify destructive recovery, and AI-backed repairs throw `InfrastructureFailure` on provider errors — why: a provider 502 during repair deleted a valid App.tsx.
- File removal during recovery is dependency-aware (`src/server/engine/structural-deps.ts`: entry, app shell, shared modules are critical and may only be replaced by prior verified content); deterministic stubs come only from the allowlist in `engine/deterministic-primitives.ts` — why: no hard-coded protected filenames, no fake business hooks.
- UI "active/complete" derives from `src/lib/turn-execution/activity-state.ts`; a terminal authoritative lifecycle overrides every local flag — why: spinners latched after failed turns.
- Failure cards derive origin/headline/action/preserved from `failure-classification.ts` via `classify()` in `friendly-errors.ts`; components never classify — why: one failure authority for every card.
- `build-phases.ts` is caption-only (labels, icons, elapsed); active/terminal state comes only from `deriveActivityState` — why: phases must never decide lifecycle.
- A project has at most one `running` turn, enforced by the partial unique index `turns_one_running_per_project` and reserved atomically by `claim_generation_turn` (via `startTurn`); a losing request gets 409 + the owner's turn id and follows it; billing eligibility is `isUnbillableTurn` — why: in-memory locks are per-worker, and check-then-insert races.
- A non-committed turn's final message comes only from `src/lib/terminal-result.ts` (`buildTerminalResult`/`formatTerminalResult`), replaces the model narration, and is persisted server-side with the assistant reply (Railway builder may insert `messages` pinned to its project) — why: the hospital failure said "everything else landed" and vanished on reload.
- The Railway agent bundle keeps `esbuild-wasm` and `typescript` external (installed as builder runtime dependencies) — why: bundling the TypeScript compiler pushed agent-core.mjs past the 10 MB commit limit.
- Missing imports are repaired at the root: `engine/missing-nodes.ts` creates each missing shared module once (exports checked against every importer) before the write gate; pages, UI kit and integration clients are never invented — why: per-importer repair looped on the hospital build.
- First-build intent comes from `prd/intent-contract.ts` stored on `Prd.intent`; router pages that diverge from the request's archetype are dropped — why: a hospital request produced a shop.
- File size is never a correctness rule (only a decomposition signal); incompleteness is decided by the parser/verifier — why: complete large files were being reverted.
- Non-success exits write the `turn_economics` record (opened as `running` at turn start, finalized with `finalizeOnly`) and the assistant reply BEFORE the terminal turn status — why: the builder may only write for a running turn, so failures vanished.
- Project exploration is read-only and deterministic (`src/server/context/explore.ts`: pure functions over a frozen snapshot, run concurrently, skipped for LIGHT and first builds); the generation executor stays the single writer — why: faster discovery without extra AI calls or a second writer.
- First-build plan validation covers the intent contract's core modules: under half covered → contract modules are added before any page is written and recorded as `turnStrategy.planCorrection` — why: the hospital plan drifted into template pages.
- The identifier gate never flags real platform globals (`isPlatformGlobal`: engine `globalThis` + ES/DOM names), not a hand-kept list — why: `Date` was reported undefined and failed a valid task app.
- Every terminal turn closes its evidence in the database (`close_turn_evidence` trigger: economics result + assistant message), whichever path ended it — why: reaped turns left economics "running" and no message.
- Unwritten pages the user did not name and the intent contract does not require are removed from the router; requested/core pages are never dropped — why: one missing optional Settings page discarded a 20-file hospital build.
- Type-only exports imported as values fail verification only when the importer uses the name at runtime (`usedAsValue`) — why: type-position imports are erased by the bundler, and the false positive discarded the bakery build.
- Missing-node recovery also runs just before the final check over all changed paths — why: helpers imported by late-written pages were never created, and quarantine cascaded through every importer.
- The undefined-identifier gate ignores names that appear only in type positions (`inTypePosition`) — why: erased types cannot throw a ReferenceError; `TaskCardProps` discarded a working task app.
- Layout words ("one-page", "landing", "website") are never extracted as requested page names — why: "a one-page landing page" demanded a /one-page route and failed the build.
- Long first builds checkpoint durably in `build_checkpoints` (shell answer + each whole page as it finishes, written only by the owning turn via `checkpoint_merge_pages`); a lost worker is marked resumable by `reap_stalled_turns`, and the resume worker continues it on the build server with `resumeCheckpointId`. Saved files are only re-staged into the new turn's transaction, so every gate and the revision-guarded commit still run — why: a lost build server threw away 39 minutes of finished hospital pages.
- First-build WRITE stage runs as work units (`src/server/engine/work-unit.ts` inside `writePlannedPages`): foundation modules first (parallel), then pages consuming REAL export signatures, each unit immediately validated (truncation → continuation from the completed portion; imports/default-vs-named → one same-writer correction) before falling to recovery; final gates + CAS commit unchanged — why: the hospital build guessed `Container` exports and discarded a cut-off Staff page only at final verification.
- Page-writer provider calls retry only 429/5xx/connection with bounded jittered backoff (`engine/provider-retry.ts`), same model — why: transient provider errors must never become code failures.
- `build_checkpoints` needs explicit service_role grants and checkpoint writes surface their result — why: missing grants made every save fail silently, so no checkpoint was ever written.
- Each first-build page unit runs the real TS undefined-name check (`undefinedNames`) right after writing; the only mechanical fix is `safeReactImportRepair` (React used solely as `React.x`), everything else goes back to the same writer once; checkpoints of non-committed turns are closed via `retireCheckpoint`/cancel trigger with `terminal_outcome`, never deleted — why: a missing React import in one page discarded 34 good files at final verification.
- App builds execute only through `src/server/engine/agent-loop.ts` `runExecutionLoop`: one `ExecutionState`, operations re-derived from the live staged workspace each iteration (foundation → pages → sections → frame), canonical page identity (`pageKey`, router adopted via `reconcileRequirements`), each op checkpointed (awaited) as it lands; `write.ts` holds instruction/fact helpers only — why: the fixed page batch + router harvest scheduled Dashboard three times and saved progress fire-and-forget.
- No AI inspector or AI critic: edit targets come from deterministic location only, and `runCritic` runs deterministic defect rules only — why: both repeated what immediate validation and final verification already know, at extra AI cost.
- Missing shared modules are created in exactly two places: inside the execution loop (first builds, re-run on each batch of newly written files) and the final check's root-cause step — why: three independent passes had no shared budget.
- Build server never rewrites source: syntax-heal runs report-only (`reportSyntax` in builder/src/fs-helpers.ts) — why: the app server's verified source is the only authority; silent builder rewrites hid defects.
