- Project code identity is `projects.revision`, advanced only inside the DB transaction that changes `project_files` (replace_project_files or per-statement file triggers); builds store `project_revision` and only a build of the current revision may affect readiness, the current-build pointer or publishing — why: stale build/verification results must never approve newer code.
- The selected design-system package is the only authority for colours, fonts, tokens and accent; the Design Director, design-taste and app-UI blocks own composition/motion only and drop their palette/font instructions when a package is selected, and generation re-applies the package to the tree before commit — why: one visual authority, no competing palettes.
- Any change under `src/server/` used by generation requires re-running `bun scripts/build-agent-core.mjs` and bumping `AGENT_CORE_VERSION` — why: Railway runs the committed bundle, and a stale bundle made a published fix never go live.
- Mobile apps, API-only backends and Chrome extensions are paused behind `src/lib/site-flags.ts` (all false): every request resolves to web (`resolveBuildTarget`), their prompts/kit paths never reach the engine, and their pages/ideas/surfaces/server actions are hidden or refuse — why: web-only launch keeps unfinished pipelines out of the stable engine; code is kept, turning one on is a flag change.
- One-click connectors use one flow in `src/server/connectors/oauth.server.ts` (HMAC-signed expiring state, AES-GCM tokens in `connector_accounts`, server-only access); a provider is shown connectable only when its developer-app secrets exist — why: one sign-in path for every provider, tokens never reach the browser.

- Domains are sold only through Domain Name API (`src/server/domain-name-api.server.ts`); Cloudflare is used only for SaaS custom hostnames/SSL. Every price comes from the registrar (search for the shortest term, catalogue `/products/tlds` for other terms and all renewals, `/renew/check` for premium) — never computed or assumed; renewals go only through `src/server/domain-renewal.server.ts` (one `domain_renewals` row per attempt, one success per expiry date) — why: Cloudflare Registrar is not a reseller platform, and renewal prices differ from first-year prices.
- Public API callers resolve once through `verifyApiCaller` (service-api.server.ts): the master key keeps full access; `sk_custard_` developer keys are stored only as SHA-256 hashes in `developer_api_keys`, reach only projects linked in `developer_key_projects`, and cannot call account-wide endpoints — why: partners need their own revocable keys without a second ownership or billing model.
- Embeddable previews live on one stable address per project (`preview--<project id hex>.sites.custardai.dev`, certificate requested on first embed); host-lookup serves the latest ready build there and narrows `frame-ancestors` to one origin only when a live `project_embeds` token arrives as `?petal_embed=` (the worker never caches token lookups) — why: deploy-time `_headers` cannot name each partner's origin, and per-embed hostnames would need a certificate each.
- Custard AI's MCP server is hand-written JSON-RPC at `/api/public/v1/mcp` (`src/server/mcp/custard-mcp.ts`, stateless, JSON replies), and every tool dispatches in-process to the existing `/api/public/v1` route handlers with the caller's own bearer key (`mcp/dispatch.server.ts`); `packages/custard-mcp` is only a stdio bridge to that endpoint — why: `@lovable.dev/mcp-js` supports only OAuth or no auth, while partners authenticate with API keys, and one copy of auth/scoping/build logic must serve REST and MCP.
- Generated mobile apps reach phone features only through the owned `src/lib/native.ts` bridge (shipped by `scaffold-kit-mobile-shell.ts`, zero native npm deps); the open-source shell and its plugins are added only at store-build time by the runner recipe — why: no vendor licence or lock-in (Despia rejected), and the preview never breaks on native imports. The bridge calls the shell's native channel (`Capacitor.nativePromise`) when no plugin registry exists, so it works when the app loads a live website.
- Per-app native settings come only from the project's optional `petal.native.json` (features from a fixed store-safe list, link hosts/schemes) plus `capacitor.config.json` `backgroundColor`, applied by the runner's "Apply app settings" step — why: one generic recipe serves every app, and tracking-type permissions can never be switched on.
