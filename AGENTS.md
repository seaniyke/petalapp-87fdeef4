- Project code identity is `projects.revision`, advanced only inside the DB transaction that changes `project_files` (replace_project_files or per-statement file triggers); builds store `project_revision` and only a build of the current revision may affect readiness, the current-build pointer or publishing — why: stale build/verification results must never approve newer code.
- Generic design/craft prompt guidance lives only in `src/server/agent-knowledge/*.md` (Webby v1.2.30, loaded unedited via `?raw`, Webby-only tool sections filtered at load time); TS keeps runtime facts and deterministic enforcement — why: one canonical source per instruction category.
- Design-system packages live only in `src/server/design-systems/packages/<slug>/` (design.json, tokens.css, accents.json, fonts.html, DESIGN.md; optional preview.html, components/), validated by `design-systems/loader.ts`, applied deterministically by `apply.ts`, selection stored on `PicDesignSystem.package` and changed only by `retheme.ts` — why: one package format, no AI-driven re-theming, no second design store.
- The selected design-system package is the only authority for colours, fonts, tokens and accent; the Design Director, design-taste and app-UI blocks own composition/motion only and drop their palette/font instructions when a package is selected, and generation re-applies the package to the tree before commit — why: one visual authority, no competing palettes.
