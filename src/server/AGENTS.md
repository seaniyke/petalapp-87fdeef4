- Generic design/craft prompt guidance lives only in `src/server/agent-knowledge/*.md` (Webby v1.2.30, loaded unedited via `?raw`, Webby-only tool sections filtered at load time); TS keeps runtime facts and deterministic enforcement — why: one canonical source per instruction category.
- Design-system packages live only in `src/server/design-systems/packages/<slug>/` (design.json, tokens.css, accents.json, fonts.html, DESIGN.md; optional preview.html, components/), validated by `design-systems/loader.ts`, applied deterministically by `apply.ts`, selection stored on `PicDesignSystem.package` and changed only by `retheme.ts` — why: one package format, no AI-driven re-theming, no second design store.
- Requirement-level progress lives only on the PRD (`Prd.requirements`, `src/server/prd/prd-requirements.ts`); status is evidence-derived (COMPLETED only from a ready, verified build of the current revision; stays valid while its files are unchanged) and written by `prd-progress.server.ts` from generation and the build callback — why: one product memory, no model-claimed completion.
- Semantic source validation uses the real TypeScript checker (`src/server/verification/identifiers.server.ts`, TS2304 only, changed files only, explicit verified/failed/unavailable — unavailable follows the syntax-gate policy and is never reported as verified) inside `verifyProposedSource`; esbuild remains the parse gate — why: parse-only validation let `ReferenceError: mode is not defined` commit and crash the preview.
- A project has at most one `running` turn, enforced by the partial unique index `turns_one_running_per_project` and reserved atomically by `claim_generation_turn` (via `startTurn`); a losing request gets 409 + the owner's turn id and follows it; billing eligibility is `isUnbillableTurn` — why: in-memory locks are per-worker, and check-then-insert races.
- File size is never a correctness rule (only a decomposition signal); incompleteness is decided by the parser/verifier — why: complete large files were being reverted.
- Non-success exits write the `turn_economics` record (opened as `running` at turn start, finalized with `finalizeOnly`) and the assistant reply BEFORE the terminal turn status — why: the builder may only write for a running turn, so failures vanished.
- The identifier gate never flags real platform globals (`isPlatformGlobal`: engine `globalThis` + ES/DOM names), not a hand-kept list — why: `Date` was reported undefined and failed a valid task app.
- Every terminal turn closes its evidence in the database (`close_turn_evidence` trigger: economics result + assistant message), whichever path ended it — why: reaped turns left economics "running" and no message.
- Unwritten pages the user did not name and the intent contract does not require are removed from the router; requested/core pages are never dropped — why: one missing optional Settings page discarded a 20-file hospital build.
- Type-only exports imported as values fail verification only when the importer uses the name at runtime (`usedAsValue`) — why: type-position imports are erased by the bundler, and the false positive discarded the bakery build.
- Missing-node recovery also runs just before the final check over all changed paths — why: helpers imported by late-written pages were never created, and quarantine cascaded through every importer.
- The undefined-identifier gate ignores names that appear only in type positions (`inTypePosition`) — why: erased types cannot throw a ReferenceError; `TaskCardProps` discarded a working task app.
- Layout words ("one-page", "landing", "website") are never extracted as requested page names — why: "a one-page landing page" demanded a /one-page route and failed the build.
- `build_checkpoints` needs explicit service_role grants and checkpoint writes surface their result — why: missing grants made every save fail silently, so no checkpoint was ever written.
- No AI inspector or AI critic: edit targets come from deterministic location only, and `runCritic` runs deterministic defect rules only — why: both repeated what immediate validation and final verification already know, at extra AI cost.
- Per-step loop telemetry lives in `tool_loop_calls` (work unit, context split, provider, TTFT, tok/s, progress); code routing adds a soft `preferred_min_throughput` (env `CODEGEN_PREFERRED_MIN_TPS`, 0 disables), never an allow-list — why: identical builds were routed to ~20–35 tok/s endpoints with no way to see it.
- Scaffold ownership is per file: `isScaffoldOwnedPath` = exact owned paths + the shipped kit manifest (`scaffoldKitManifest()`, overwrite KIT_FILES + static backend packs); only fully generated `src/integrations/backend/` stays prefix-owned; readiness and commit both use `projectAuthoredFiles` — why: a blanket `src/components/blocks/` prefix hid a model-authored block from the verifier and failed a valid bakery build.
- The first-build loop's runaway ceiling is size estimate × headroom, where the size estimate is the p90 of measured first-build TOKENS (`firstBuildTokenSamples`) priced at the loop's model by `engine/loop-cost-estimate.ts` (max with the class estimate); the loop checks max(predicted next call, largest call) before every call, including the first; every AI cost uses `modelPricePerM` with the gateway cache-read rate — why: flat DeepSeek-era class dollars stopped every gateway first build after one step, and ignoring cached tokens overstated cost about 3×.
- Build settlement prices from the durable per-call records (`ai_call_log` via `readTurnCallCosts` → `priceRecordedCalls`) after `flushCostWrites()`; post-turn stage "after" calls are unbilled overhead; `min_charge_credits` (0.30) is a floor, never a flat price — why: in-memory usage missed the setup calls and the last write could land after the charge.
- An edit is site-wide (every page pinned, page/layout protection off) only when `detectCrossCuttingIntent` fires; a structural edit scope alone never makes it site-wide — why: single-page structural edits were sending the whole app and dropping write protection.
- Example kit files (`src/components/examples/`) are never overwritten during edit turns (removed from `shouldOverwriteDuringPatch`); `IMAGE_REF_RE` also matches `data:image/*` so resolved pictures count as filled slots — why: overwriting them re-opened picture slots and produced phantom file writes the AI never made.
- Product structure (`surface`: public / app / public+app) is decided deterministically on the intent contract (`deriveProductSurface`) before any page is written; public+app puts Home + /login in front and moves the app home to /dashboard; the restaurant family applies only when an app is clearly requested — why: management systems with public users produced only the internal dashboard, without turning plain websites into apps.
- Responsive checks (`verification/responsive.ts`) are advisory only: attached to the verification record and logged, never change the verdict; Playwright on the build server stays the evidence — why: a regex must never reject a valid app.
- Archetype/blueprint routes are advisory only: generate.ts never pushes them into plannedRoutes; required routes come only from user-named pages, the intent contract and the product surface — why: template route lists failed builds as "missing requested pages" for products outside the known domains.
- Shared-tier apps bake `sharedApiOrigins()`: configured origin, then Petal's published address, then the stable project alias; kimble.cloud and buildwithpetal.com are filtered out — why: kimble.cloud answers 404 and buildwithpetal.com rejects valid keys, and a failed request on page load makes the build server refuse to publish.
- With Kimble Cloud on, the signed-in area (/dashboard…, or everything but auth pages when app-only) must be wrapped by the kit's `RequireAuth` (shipped in the generated `integrations/backend/auth.tsx`); the routes gate fails otherwise — why: signed-out visitors could open /dashboard.
- The Railway server move happens at build time when the app needs its own server (`considerCompute` after `recordTierIntent`); the daily watcher is only a backstop for compute-intent apps — why: the watcher ran once a day and only over shared apps, so heavy apps never moved.
- The origin handed to the build server comes only from `trustedAppOrigin` (`src/server/public-origin.ts`: private/localhost/non-https → `PETAL_PUBLIC_ORIGIN` or the published app) — why: preview requests sent the VPS a `localhost` callback that pointed at the VPS itself.
- TypeScript's `__filename`/`__dirname` globals are installed by `installTsRuntimeGlobals()` in the server request middleware (src/start.ts), plus the import-order shim in `identifiers.server.ts` for Node — why: in the Worker bundle TypeScript is a separate chunk evaluated before the importing module's body, so the import-order shim alone still crashed every live generation turn.
- Custard AI's v1 generate always follows a succeeded turn into its build through the idempotent `/api/builds/trigger` and reports it (`build` SSE events + `build.completed` webhook with `deploymentUrl`); status is readable at `GET /api/public/v1/projects/:id/builds` — why: the caller got code but never the live address.
- Custard AI apps (owned by the service account) get the staff widget via `injectCustardWidget` at the `postBuildToRailway` boundary, using the sanitised tag stored on `projects.custard_widget_tag` (from the public generate call's `widgetTag`/`agentId` or a tag in the prompt) so `data-agent`/`?agent=` survive the machine-owned index.html, and `turn.completed` is sent after the build with `previewUrl`/`preview_url`/`publishedUrl` — why: Custard's canvas needs the live address in the turn event and status.
- Custard AI billing (`/api/public/v1/billing`, `/projects/:id/billing`, `billing` on turn status and `turn.completed`) is derived only from `credit_ledger` + `turn_economics` via `service-billing.server.ts`, in credits, never exposing internal USD provider cost — why: one ledger is the bill; Petal margin stays private.
- Product surface strips negated app words ("no accounts", "without login") via `withoutNegatedAppWords` and treats "website only / just a website" as public — why: the Aura run "Website only, no accounts" was given accounts and a database.
- On the Cloudflare Worker the esbuild verifier parse gate uses the TypeScript parser (no WASM in the server bundle); Node keeps esbuild-wasm — why: the Node entry spawns a process and refused to run bundled, failing every live build at final validation.
- Bracketed text after a page name ("Home (hero, testimonials)") lists sections of that page, never pages; only "pages (A, B)" is a bracketed page list (`extractRequestedPages`) — why: the Aura run built Philosophy/Testimonials/Hero as separate pages and dropped the real ones from the list.
- The build callback must answer the build service inside its callback wait (`src/lib/build-callback-budget.ts`): AI reviews before "ready" share `PRE_READY_BUDGET_MS` and fall back to deterministic verdicts — why: the host cancels the handler when the build service hangs up, so a live site stayed "pending" through every retry.
- Background jobs read `BUILDER_SHARED_SECRET` from the vault; after rotating the secret, call `sync_builder_cron_secret` (service role) with the new value — why: a stale vault copy made the build watchdog and turn-resume jobs fail with 401 for hours, so no stuck build was ever recovered.
- A remembered picture fills a slot only when it shows essentially the same subject (`fitsRequest` "slot": most request words and most picture words agree); one build never gives two slots the same picture (`usedUrls`); shared builder accounts (Custard service user) never reuse across their projects; unimported `src/components/examples/` files get no pictures — why: the live Aura site got 2 pictures for 8 project cards, matched on the single word "dark" from another customer's project.
- A first build's tab name, site icon and theme colour are written at the commit point by `ensureSiteIdentity` (PRD product name, then header wordmark) — why: cleanup restores Kimble-owned index.html, so the live site kept "App".
- Customer-facing source is checked on every build-loop write by `verification/customer-privacy.ts` (data calls, not button labels): no seeding/listing of people's records (bookings, orders, messages…) except `{ mine: true }`, no visitor update/remove of them, no visitor writes to the catalogue; findings go back to the same writer — why: Allure Bar showed every visitor other customers' bookings and a disguised "add product" form.
- The starter kit ships no decorative effects layer (no `@/components/fx`, marquee, gradient text/blob, gradient hero or faux-window blocks); prompts say they do not exist — why: they kept producing dated, cluttered sites.
