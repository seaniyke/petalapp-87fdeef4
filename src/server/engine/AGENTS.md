- Repair turns are classified BEFORE the design/PIC stages in `/api/generate` (`isRepairTurn`): they reuse the committed design direction via `readDirectionFromMemory` (never re-pick), skip structural-turn treatment, and emit truthful stage labels — why: a runtime-error repair must never restart first-build stages or disturb the design contract.
- File removal during recovery is dependency-aware (`src/server/engine/structural-deps.ts`: entry, app shell, shared modules are critical and may only be replaced by prior verified content); deterministic stubs come only from the allowlist in `engine/deterministic-primitives.ts` — why: no hard-coded protected filenames, no fake business hooks.
- Missing imports are repaired at the root: `engine/missing-nodes.ts` creates each missing shared module once (exports checked against every importer) before the write gate; pages, UI kit and integration clients are never invented — why: per-importer repair looped on the hospital build.
- First-build intent comes from `prd/intent-contract.ts` stored on `Prd.intent`; router pages that diverge from the request's archetype are dropped — why: a hospital request produced a shop.
- Project exploration is read-only and deterministic (`src/server/context/explore.ts`: pure functions over a frozen snapshot, run concurrently, skipped for LIGHT and first builds); the generation executor stays the single writer — why: faster discovery without extra AI calls or a second writer.
- First-build plan validation covers the intent contract's core modules: under half covered → contract modules are added before any page is written and recorded as `turnStrategy.planCorrection` — why: the hospital plan drifted into template pages.
- Long first builds checkpoint durably in `build_checkpoints` (shell answer + each whole page as it finishes, written only by the owning turn via `checkpoint_merge_pages`); a lost worker is marked resumable by `reap_stalled_turns`, and the resume worker continues it on the build server with `resumeCheckpointId`. Saved files are only re-staged into the new turn's transaction, so every gate and the revision-guarded commit still run — why: a lost build server threw away 39 minutes of finished hospital pages.
- First-build WRITE stage runs as work units (`src/server/engine/work-unit.ts` inside `writePlannedPages`): foundation modules first (parallel), then pages consuming REAL export signatures, each unit immediately validated (truncation → continuation from the completed portion; imports/default-vs-named → one same-writer correction) before falling to recovery; final gates + CAS commit unchanged — why: the hospital build guessed `Container` exports and discarded a cut-off Staff page only at final verification.
- Page-writer provider calls retry only 429/5xx/connection with bounded jittered backoff (`engine/provider-retry.ts`), same model — why: transient provider errors must never become code failures.
- Each first-build page unit runs the real TS undefined-name check (`undefinedNames`) right after writing; mechanical fixes are `safeReactImportRepair` and `engine/missing-import-repair.ts` (adds an import only for a TS2304-proven name with exactly one provider: React, the project's own router, or a unique kit owner — a fixed list of real lucide-react icons when the project uses lucide-react, never app modules), everything else goes back to the same writer once; checkpoints of non-committed turns are closed via `retireCheckpoint`/cancel trigger with `terminal_outcome`, never deleted — why: a missing React import in one page discarded 34 good files at final verification.
- Missing shared modules are created in exactly two places: inside the execution loop (first builds, re-run on each batch of newly written files) and the final check's root-cause step — why: three independent passes had no shared budget.
- One persistent tool-calling loop (`src/server/engine/tool-loop.ts` `runToolLoop`) is the only build executor: model picks tools, reads concurrent, writes serial, every write validated; `finish` = loop-local gaps (tasks, failing writes) + the injected `readiness` (same proposed-tree transform + `verifyProposedSource` commit uses, read via `verification/readiness.ts` `readinessOf`, also used by commitTurn); STABLE foundations (clean + a clean importer, derived from the workspace import graph, no filename rules) cannot be wholesale replaced and targeted edits that regress readiness roll back; loop-finished + commit-failed is logged as `readiness_divergence` — why: the bakery agent finished while the final verifier rejected a layout it had rewritten.
- First-build loop context comes only from `src/server/engine/first-build-context.ts` `assembleFirstBuildContext`: always-on + task-conditional knowledge in a stable `system`, everything else (manual sections, skills, design-taste, gating) as read-only `knowledge/*.md` reference docs retrieved with read_file; reference paths are unwritable; no token ceiling, sizes only reported — why: the whole edit-mode prompt (~45k tokens, with write_project contradictions) was resent on every loop step.
- Tool-loop telemetry goes only through `src/server/engine/loop-telemetry.ts` (`createTelemetrySink`: non-blocking, every failure logged as structured `telemetry_persist_failed` + counted on `turnStrategy`; `summarizeExecution` → `turnStrategy.executionSummary`); every table the build server writes needs a `TABLE_RULES` entry in `agent-db-scope.ts` — why: a missing gateway rule silently dropped every `tool_loop_calls` row.
- First builds get a deterministic starter-kit map (`renderStarterKitMap` in `engine/template-contract.ts`: path, exports, one-line purpose, no contents) and the loop answers identical re-listings as unchanged and signals exploration drift (`detectExplorationDrift`, widening/wasted inspection during an idle streak, no read-count cap) before the unchanged no-progress stop; build summaries come only from `runWithExecutionSummary` for every terminal state — why: an open-ended "batch your reads" rule made the bakery build explore 21 kit files and stop with zero writes, and failed runs lost their summary.
- First builds have no model-kept task list (`plan_tasks` removed): required work comes from the readiness authority (requested routes/intent), completion from validated workspace state; known starter-kit symbols imported from the wrong kit module are moved deterministically by `engine/kit-import-repair.ts` (exact export map from shipped kit files, exactly-one owner, never app modules) — why: the bakery run spent 3 planning calls restating the request and 3 correction calls on `SlideUp` from `fade-in`.
- Kimble never makes the model rediscover known facts: the starter-kit map carries each kit file's full public API (exports, prop/item types, variants; `kitFileApi` in `engine/template-contract.ts`), the tool loop pushes the whole-workspace readiness verdict after every write step (cached per tree, reused by finish), and first-build setup calls (PRD, design direction, PIC understanding) run concurrently because each depends only on the brief — why: the bakery run spent 11 of 19 loop calls re-reading the kit and 1m47s waiting on independent setup calls in series.
- A first-build app frame is complete with routes + navigation + either a site footer or a sidebar (`<aside>`) frame (`frameIsComplete`) — why: the CareDesk clinic app (sidebar dashboard) was rejected for having no footer; footers belong to websites, not apps.
- Whether a first build needs Kimble Cloud is decided by the intent contract's product surface (`app`/`public+app` → shared backend, websites → none unless visitors send something to the business — stay/booking requests, enquiries, contact forms, RSVPs — which keyword detection in `intent-registry` also attaches it for) before any page is written; `resolveIntentActions` returns the real provisioning outcome (`cloud.status`), chat statuses report only that outcome, and cloud provisioning is recorded as its own `cost_events` row (`stage: cloud_provision`, basis UNKNOWN until measured), never mixed into AI/build pricing — why: apps were built as static UI with no accounts, and cloud costs must never be invented or blended with AI economics.
- A first build that stops part-way (no_progress / incomplete / breaker) keeps its validated writes: the checkpoint becomes `resumable` with `terminal_outcome='partial'` (`src/lib/partial-build.ts` `keepPartialWork`), the kept files are billed once via the effort curve (`effortTrees`; a resuming turn treats them as baseline), the next first-build request auto-claims it, and nothing uncommitted enters the project — why: a stopped delivery build discarded valid pages and charged 0.
- The tool loop answers re-reads of unchanged files from state (`rereadNotice`, cleared on compaction) and its single no-progress signal carries the readiness remaining-work list — why: the delivery build spent 8 steps re-reading its own files with no stated next item.
- When Kimble Cloud is on for a first build, a routed page that reads a sample/mock data module without reaching `@/integrations/backend/client` fails the routes gate (`sampleOnlyPages`, `requireLiveData`) — why: the delivery app shipped every data page on mock-data.ts with an empty database.
- A file the current readiness verdict blames is never treated as a STABLE foundation (`blockedByReadiness` in `engine/tool-loop.ts`), and the app-subtype prompt only permits a mock-data module when no backend is attached — why: syntactically clean sample-data pages were refused as stable, so the delivery build could never rewrite them against Kimble Cloud.
- Route addresses come from `<Route>` nesting (`engine/route-paths.ts` `resolveRouteTree`); on first builds a link in rendered code (reachable from the router) to an address no page serves fails the routes gate, and a catch-all never makes a link real — why: the salon app linked /services while the page lived at /dashboard/services, hidden by a catch-all Home.
- Cognitive model tiering: first builds use `defaultFirstBuildModel()`; edits route by `classifyTaskDifficulty` → `modelForDifficulty` (`src/lib/ai-model-config.ts`): short micro-scope edits take the micro lane (fast model, one-file context); site-wide, multi-part, structural or long-brief edits get the frontier model, others the fast code model, utility model never writes code; router candidates are configured ids only — why: unconfigured slugs were silently coerced to flash, so hard edits never escalated.
- First-build pages never render their own site header+nav or announcement bar (`verification/structure.ts`, routes gate, requireShell only) — why: stacked bars over the shared header are a common AI layout defect.
- Data-backed first builds (shared tier) load lists via the kit's `db.seedOnce` (writes realistic rows only into an empty collection) per `STARTER_DATA_RULE` in `engine/first-build.ts` — why: apps opened with blank tables; seeded rows are real saved data, never hardcoded arrays.
- A dropped model reply stream keeps every complete tool call already received (`parseToolStream` → finishReason `stream_interrupted`, charged at the estimate) and re-sends once only when nothing usable arrived (`MAX_STREAM_RESENDS`) — why: Gemini 4 Argon delivers each tool call whole with ~60s silences, and one lost connection failed the whole Ember & Oak first build.
- Public-site first builds preload the page-composition, section-architectures and motion skills (`conditionalSkills`); only explicit dark/nightlife words select the dark design package, never "luxury"/"premium" — why: left on-demand the model never read them, and "luxury" turned a bright clinic black-and-gold.
- Only defects that break a running app (syntax, broken imports, undeclared names, missing requested pages, missing shell, unguarded app area) may FAIL the routes gate; dead links, duplicate page chrome and sample-only pages are WARNING advisories; edit_file falls back to a unique whitespace-tolerant line match; three identical finish refusals stop the loop (`REPEATED_REFUSAL_LIMIT`) — why: cosmetic findings and checker defects trapped the Mira Beauty build in 51 calls and discarded finished pages.
- Turn limits (`TURN_LIMITS`, `RECOVERY_LIMITS`, `MAX_REPAIRED_FILES`, repair cost ceiling, breaker counts) are runaway guards sized far above a large build, never the normal stop; at commit, a file that still fails verification may only return to its prior verified content (`engine/resilient-fallback.ts` via `commitTurn` `fallbackFor`), never a placeholder/stand-in page, and the tree is re-verified — why: micro-quotas and all-or-nothing rollback stopped paid builds part-way and discarded good pages.
